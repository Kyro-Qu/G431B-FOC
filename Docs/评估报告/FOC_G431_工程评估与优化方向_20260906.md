## 0. 总体结论

架构成熟度高：快/慢环分层、硬/软双过流、Tustin+条件积分抗饱和、dq 解耦、死区补偿、弱磁电压/电流圆、梯形轨迹、三窗口最小二乘测速+二阶 PLL、在线 Rs/Ls 辨识、抗齿槽表（**本次确认已标定、使能并写入 Flash**）、实时母线+UVLO/OVLO、黑匣子、IWDG、CPU 统计、CAN-FD 框架，均为真实落地而非空壳，整体对齐 ODrive/VESC、明显强于 SimpleFOC。

**硬件链路本次实测健康**：开环 V/F 30RPM 平稳旋转无故障，平均相电流 ≈0.65A、峰值 ≈1.0A，三相和≈0；母线稳定 14.46V；采样链 cs_ready=1、零漂 ±0.1A；DAPLink 读到器件 ID=0x468（STM32G4）、Flash=128KB、UID 正常。

当前**没有致命缺陷**，制约项集中在 4 类：①1 个仍存活的状态量缺陷（抗齿槽前馈缺门控）；②RAM 余量已到 7%；③CLI/帮助/文档与代码大面积漂移；④低速闭环整定这个"性能最后一公里"尚未收尾。按 §6 路线推进即可。

## 3. 问题清单（按优先级，均含证据与修改方向）

### 【P1 · 控制状态量】抗齿槽"前馈"缺状态门控，iq_ref 在 VF/CALIB/ident 下被积分到限幅

**现象（实测，可复现）**
1. 零目标、转子静止，`enable`（VF）后用遥测逐帧看 iq_ref：
   `0.000 → −1.803(50ms) → −3.751(100ms) → −5.200(150ms) → 永久钉在 −5.200A`，斜率约 −37A/s。
2. 每次 `ident` 结束回 IDLE，status/遥测残留 **iq_ref=−5.200A、vd=0.150V**（实流 iq≈0），连做两次均复现；`disable` 后才归零。

**根因（源码）** `Core/foc_motor.c` 慢环：
- L525-527 VF 分支 `case OPENLOOP_VF: default: break;` —— **不重算 iq_ref**；CALIB(ident) 同理。
- L536-538 前馈注入只判钩子非空，**没有像采样钩子 L531 那样限定 `state==RUN`**：
  ```c
  if (m->anticog_hook != 0) m->iq_ref += dir * m->anticog_hook(m->theta_mech);
  ```
  转子角度固定时前馈是常量，每 1ms 累加一次，~150ms 爬到 ±max_current(5.2A) 限幅。抗齿槽表本次恰好 enable=1，该路径被激活（表为 0 时不显现）。
- `App/foc_ident.c:52-60 ident_cleanup()` 只 `openloop_hold(0,0,0)`+恢复限流+置 IDLE，**不清 iq_ref/id_ref/v_dq**，故残留带入 IDLE。

**影响**：VF/开环/ident 不用 iq_ref 输出电压，所以**不影响运动安全**；但①status/遥测 iq_ref 在这些状态下是错误值，会误导调试（前两份报告看到的"VF iq_ref=3.653 残留"正是同一机理，当时只在停机切换处清零，未除根）；②若将来任何保护/逻辑在这些状态读 iq_ref 会被欺骗。

**修改方向（小改、不动算法主体）**
1. `foc_motor.c:536` 前馈加闭环运行门控，与 L531/L? 死区补偿一致：
   ```c
   if ((m->anticog_hook != 0) && (m->state == FOC_STATE_RUN)
       && (m->mode != FOC_MODE_OPENLOOP_VF)) { ... }
   ```
2. `foc_ident.c ident_cleanup()` 末尾补 `m->id_ref=m->iq_ref=0; m->v_dq.d=m->v_dq.q=0;`（或直接复用 disarm 的状态归零）。
3. 回归：enable(VF,零目标) 后 iq_ref 应恒 0；ident 结束 IDLE 的 iq_ref/vd 应 0。

### 【P2 · 资源】SRAM 余量仅 7%，栈 1KB 偏紧，黑匣子占 1/3 RAM

**证据** map：静态 30440/32768B，剩 2328B；栈预留 1024B；黑匣子 5×float[512]=10KB（`foc_motor.c:61-67`）。Cortex-M4F 快环 ISR 有较多 float 局部量，且 ADC ISR 可抢占低优先级 ISR，1KB 栈 + 仅 2.3KB 总余量，**没有任何栈越界硬件保护**，后续加特性（双轴/观测器/CAN 队列加深）极易静默踩内存。

**修改方向**
1. 黑匣子 `FOC_BLACKBOX_LEN` 512→256（故障前 16ms，对 16kHz 抓过流波形仍足够），**直接省 5KB**；或把 5 通道压成必要的 3~4 通道。注意同步修正 `foc_motor.c:1175`、`foc_motor.h:227` 里"256 拍/16ms"与"512/32ms"互相矛盾的注释。
2. 加**栈高水位检测**：启动时在栈底填 0xA5 哨兵，主循环统计剩余栈，接 telemetry 或 status；当前完全看不到栈用了多少。
3. 若要保留 512 黑匣子又加功能，建议把大缓冲改为"故障时才落/按需编译"，或评估换更大 SRAM 的 G4 型号。

### 【P2 · CLI】help 被 1024 发送缓冲确定性截断，且漏列 blackbox/obs 命令

**证据（实测+源码）**
- 在线 `help` 每次都在同一位置 `conf <write|eras` 截断；脚本解析帮助字符串字面量 **=1095B > `CMD_TX_BUF_SIZE=1024`**（`App/foc_cmd.c`），`vsnprintf` 超限被截到 1023。
- `blackbox`（L961）、`obs`（L981）命令**已实现但帮助文本（L215-242）里根本没有**，属于"隐藏命令"。

**修改方向**：`CMD_TX_BUF_SIZE` 1024→1408（或 help 分两次 print）；把 blackbox/obs 补进帮助；顺手统一帮助里 `log [0|1]` 等被截断的行。

### 【P2 · CLI】`cli_rx_overflow` 是死计数器，超长输入行被静默丢弃

**证据** `foc_cmd.c`：`rx_queue_overflow_count` 只在 L47 声明、L174 status 打印、L190 当参数，**全工程无任何自增**；`CMD_RX_QUEUE_SIZE 256`（L34）定义后未使用（实际只有单行 64B 缓冲）；行超长走 else 直接丢字符、无计数无提示。
**修改方向**：在行溢出分支 `rx_queue_overflow_count++`（让 status 字段名副其实），或删除该假字段与未用宏，二选一，避免"看着有诊断其实永远是 0"。

### 【P3 · 可观测性】CAN 框架在但默认关闭，且无任何串口观测入口；存在同名旧文件

- `HAL/foc_config.h:189 FOC_CAN_ENABLE=0`（协议不启动，CubeMX 仍初始化 FDCAN1 外设）。`Driver/can/foc_can.c` 设计完善（ISR 只入队、序列号幂等、bus-off 自恢复、diag 计数），但这些 diag **只能 Keil Watch 看，CLI 无 `can` 命令**，将来启用后排错会很被动。
- `Driver/can/foc_can.c(25KB,在用)` 与 `Reserve/foc_can.c(4.4KB,旧版)` **同名并存**，易混。
- `Core/Src/main.c` CubeMX 写死 `FrameFormat=FDCAN_FRAME_FD_BRS`，而 `FOC_CAN_BRS_ENABLE=0`（G4 的 BRSE 只是"允许 BRS"，每帧是否 BRS 由 TxHeader 按宏决定，故功能无碍，但建议注释说明或交由宏控制，避免误读）。
- **方向**：预留一个只读 `can` CLI（打印 rx/tx 计数、错误、bus-off、版本/状态）；删除或归档 Reserve 旧文件。

### 【P3 · 可观测性】缺"在线参数回读"，`conf` 只能写/擦

`conf` 仅 write/erase，没有 read/dump；在线 Rs/Ls（ident apply 后）、各环整定值没有一条命令整屏回读（前一份复核报告也只能靠链路推断在线 Rs/Ls）。**方向**：加 `conf read` / `param`，一屏打印 params+三环 PID+滤波器+校准+acog 版本，便于"调的是不是这份参数"核对。

## 4. 文档/注释与代码漂移（实测逐条命中，建议集中清扫）

> 这类问题不影响运行，但会显著拖慢后续调试与交接，且多条已被我用板子证伪。

1. **调参手册教的是已失效的旧短命令**：`Docs/08` 用 `id/id a、cb、vp/vi、m vel、e 1、t、s、c full、save/save e`，在线实测 `id/cb/vp/vi/save/t` **全部 `unknown`**；现命令为 `ident(apply)、current bw、vel kp/ki、mode、enable、target、status、calib full、conf write/erase`。`Docs/04` 大概率同样，需通篇替换。

3. **架构文档过时**：`Docs/02` 称"Core 零硬件依赖、可 PC 单测""校准结果不存 Flash""暂不做无感"——现状是 Core 已 include HAL 头（见 §5）、校准/参数/acog 都存 Flash、观测器已可 `obs` 在线切换。

   - 观测器注释 Rs=0.395Ω/Ls=301µH，而实际用 params=0.437/336，本次 ident=0.402/321（三套值并存，建议以一份"电机标定记录"为准）。

## 5. 架构/性能层面的优化点（非缺陷，面向下一步）

1. **Core→HAL 反向依赖（破坏自家分层铁律）**：`Core/foc_motor.c:13-14` include `../HAL/foc_config.h`、`../HAL/foc_board_g431.h`，并在 L196 调 `foc_board_cycles()`（DWT 周期计数，用于观测器切换 1s 窗口）。`Docs/02` 铁律要求 Core 不依赖板级、可 PC 单测。**方向**：把"取周期/时间"做成接口（经 `foc_types.h` 函数指针注入，或 init 时传入 `uint32_t(*now_cycles)(void)`），删掉 Core 对 board 头的 include，恢复可移植/可单测。
2. **快环三角函数**：每拍 1 次 `sinf/cosf`（`foc_transform.h`）。当前 CPU 空闲 7.5%、VF 峰值 40.6%，闭环+观测器+弱磁同时上会更高。**方向**：换查表插值/CMSIS-DSP `arm_sin_cos_f32`（注释原本就这么打算）或定点 fast trig，给高负载留余量；改前后用 g_foc_cpu_diag 对比峰值。
3. **电流环纵深（前序已提，仍列为长期项）**：电流环 `out_ramp=0`（输出可单拍跳变，P0 修复后仅剩比例阶跃，风险已可控）；可选项①非零电压斜率限制、②u_dc 单拍快速跌落快通道（不等 UVLO 100ms 防抖）、③片内比较器+DAC 阈值+TIM1 BKIN 逐周期硬件限流（应对桥臂直通/真短路的最后防线；G4 比较器阈值可用片内 DAC，无需外接，工作量在采样点接线与 BKIN 时序）。
